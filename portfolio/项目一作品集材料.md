# 项目一｜知页 · AI 知识库助手

这份材料用于面试和作品集展示。说话时可以按自己的真实分工调整“我负责”的部分；数字来自仓库里的开发评测，不把开发集结果说成线上准确率。

## README 的求职视角检查

现在的 README 信息比较完整，安装方式、检索方法、引用规则、无答案处理和局限都写到了。它更像一份给开发者看的说明书，第一次打开的人需要读一段时间才能知道这个项目解决什么问题。

建议把 README 的前几行按下面的顺序表达：

1. 先说场景：用户把一份制度或课程资料交给助手，希望得到能回到原文核对的答案。
2. 再说体验：上传文件或打开示例，提问、追问，展开来源查看页码或段落位置。
3. 最后说亮点：支持 PDF、Word、TXT；有关键词和语义两种检索；资料不够时会明确提示。

README 中已经有不少边界说明，这是优点。面试时不要把“可追溯引用”说成“事实绝对正确”，也不要把 20 道开发题的 20/20 说成产品准确率。可以把评测集、样本数量和限制一起讲出来，可信度会更高。

## 3—5 分钟演示脚本

### 0:00—0:30：先交代问题

“我做的是一个面向内部资料的文档问答工具。普通聊天模型能回答很多常识问题，但遇到员工手册、报销规定这类材料时，用户更关心答案是不是来自手里的文件。所以我把重点放在三件事上：能找到相关原文，回答能回到具体位置，资料没有答案时不要硬编。”

### 0:30—1:10：打开示例

打开应用，侧栏开启“使用内置示例”。

“这里放了一份虚构的员工手册，所以不需要先准备文件。真实使用时可以上传 PDF、Word 或 TXT，系统会在读取时保留文件名、页码、段落或表格行。”

### 1:10—1:50：演示首轮回答

提问：`正式员工每年有几天年假？`

“这是一个直接问题。系统先从文档中找相关片段，再把候选原文交给模型。回答下面有‘引用原文’，展开后可以看到‘正式员工每年享有十天带薪年假’，以及它在示例文件中的位置。引用不是模型自己写一个页码，而是程序检查来源编号和摘句确实存在于检索到的原文中。”

### 1:50—2:30：演示多轮追问

提问：`那试用期员工呢？`

“这一句单独拿出来不完整。系统先把它改写成‘试用期员工享有年假吗？’，再重新检索。页面会显示本轮理解的问题，方便发现改写是否偏了。历史回答只帮助补全主题，不直接作为新一轮的证据。”

### 2:30—3:00：演示资料不足

提问：`公司提供免费午餐吗？`

“员工手册没有午餐条款，所以页面提示当前资料不足，并把候选原文单独放在‘候选原文’里。它不会把相似但无关的内容当成引用。这和‘关键词没有找到结果’是两种情况，服务报错也会单独显示。”

### 3:00—3:40：说明两种检索

“关键词检索使用 BM25，适合问题里直接出现原文词语的情况；语义检索用本地 BGE-small-zh-v1.5 生成向量，更适合‘垫的钱要怎么报回来’这类换一种说法的问题。语义相似度只负责排序，我没有用一个未经验证的分数阈值来判断‘一定有答案’，最终是否能回答还要看原文和引用检查。”

### 3:40—4:30：讲清楚实现和验证

“文档读取后先按段落组织，长段落再按句子拆分，块大小控制在 400 字符左右，同时保存 PDF 页码、Word 段落或表格行。回答模型只输出结构化 JSON，程序检查 answerable、来源编号和连续摘句。当前共有 57 项自动测试。20 道虚构政策开发题中，修改模型调用参数和追问提示后，14 道有答案题给出回答，6 道资料缺失或冲突题正确返回提示；这个结果只说明这批开发题通过，不能当成独立准确率。”

### 4:30—5:00：主动说局限

“现在的记录保存在当前会话内存中，还没有账户、数据库和权限系统；扫描版 PDF 也没有接 OCR。引用能证明摘句来自文件，但不能自动证明模型对摘句的解释一定正确。下一步如果要接近生产使用，我会先准备没有参与调试的长文档和人工标注问题，再评估检索召回、错误拒答和条件遗漏。”

## 简历项目描述

### 一句话版本

知页｜AI 知识库助手：用 Streamlit 构建面向 PDF、Word、TXT 的文档问答工具，支持关键词/语义检索、多轮追问、可定位原文引用及资料不足提示。

### 适合简历的四条描述

- 负责搭建文档问答流程：解析 PDF、Word、TXT 并保留页码、段落和表格行位置，按段落及句子切分为约 400 字符片段，减少跨段引用不清的问题。
- 实现 BM25 关键词检索与本地 BGE-small-zh-v1.5 + Chroma 语义检索，支持在同一文档中切换检索方式，并复用文档索引。
- 设计结构化回答和引用检查：模型返回可回答标记、结论、来源编号和连续摘句；程序核对来源及摘句，区分已回答、资料不足、无匹配、未核验和服务错误。
- 加入最多三轮历史问答的追问改写、会话导出、文档切换确认和模型异常处理；57 项自动测试通过，20 道开发集在调整调用参数和提示后全部通过预设状态/事实检查，单题耗时中位数由约 14.4 秒降至约 1.8 秒。

### 面试中更稳妥的项目介绍

“我做了一个文档问答应用，目标不是让模型自由发挥，而是让回答尽量回到用户上传的材料。我的主要工作包括文档结构保留、两种检索、追问改写和引用检查。实现时我把‘没有检索到’、‘检索到了但资料不足’和‘模型返回格式不可靠’分成不同状态，用户能知道下一步应该换关键词、补资料还是重试。开发集上的结果是 20 道题全部通过，但它是参与调试的虚构数据，所以我会把它当作回归检查，不把它当作泛化准确率。”

## 面试官可能追问的问题

### 1. 为什么同时做关键词检索和语义检索？

关键词检索对专有名词、数字和条款编号很直接，也不需要下载模型；语义检索对同义表达更友好。两者解决的问题不同，所以我把它们做成可切换选项，而不是假设一种方法在所有文档上都最好。当前开发样本里，关键词检索让 14 道有答案题中的 13 道进入前三，语义检索是 14/14；样本很小，只能说明方向。

### 2. 为什么不把整份文档直接发给模型？

整份文档会增加输入成本，也让模型更难区分相关条款。分块后先检索少量候选片段，回答范围更明确，引用也能对应到具体片段。代价是切分可能把一条规则拆开，所以我优先保留完整段落，长段落才按句子拆分，并保留少量重叠。

### 3. 400 字符是怎么决定的？

这是在当前模型上下文、回答长度和引用完整性之间取的工程折中，不是理论上唯一的最佳值。太小容易丢掉适用条件，太大则会带入更多无关内容。代码把段落当作优先边界，长段落按句子拆分，并用测试和实际样例检查召回效果。

### 4. 你说的“引用验证”具体验证什么？

模型需要返回来源编号和连续摘句。程序先检查 JSON 格式，再检查编号是否指向本轮检索到的来源，最后用空白归一化后的文本匹配摘句。通过后才把结论和引用一起展示。它能防止模型编造页码或引用不存在的句子，但还不能完整判断模型有没有错误理解真实摘句。

### 5. 检索不到和资料不足有什么区别？

关键词检索没有候选结果时是 `no_match`，程序不会再调用回答模型；有候选片段但它们不能支持问题时是 `insufficient`，页面会展示候选内容但不把它们标成证据。这样用户知道是换关键词，还是需要补充文档。

### 6. 多轮追问怎样避免把上一轮答案当成事实？

追问先单独调用模型改写成可检索的问题，提示里要求只补全指代和主题，不能把历史答案里的数字或附加条件拼进去。随后仍然只用当前文档检索和生成，历史答案不进入回答证据。页面还会显示改写结果，让用户可以检查。

### 7. 为什么有时回答会拒答？

当关键数字、适用对象缺失，或原文出现无法解决的冲突时，拒答比猜测更安全。但“用户没说自己的身份”不代表政策无法说明，所以现在允许回答“该条款适用于正式员工”，同时不替用户假定身份。这个边界需要通过具体样例持续调整。

### 8. 你遇到过什么真实的模型问题？

有一次服务返回 HTTP 成功，但正文为空，检查响应发现 `finish_reason=length`，1500 个输出 token 全部消耗在 reasoning 上。后来按 TokenHub 参数显式关闭思考模式，并在代码中把空正文和长度截断标记为服务错误，不再误报成资料不足。这个问题也加入了自动测试。

### 9. 为什么使用本地向量模型，而不是把文档全部交给云端 Embedding？

当前项目希望让文档向量计算留在运行机器上，减少额外服务依赖和费用；真正回答时仍会把候选原文发送给配置的在线模型。这个选择并不等于完全离线，也需要在 README 中明确说明数据边界。生产场景还要根据数据敏感程度、机器资源和延迟重新取舍。

### 10. 如果继续做成产品，你会先改什么？

我会先做独立评测，而不是继续堆功能：准备未参与调试的长文档，标注问题、证据、适用条件和应拒答的问题，分别统计召回、引用通过率、错误回答和错误拒答。然后再考虑账户、权限、数据库持久化、OCR、限流和监控。现在的 20 道题只能作为开发回归检查。
