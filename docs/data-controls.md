# 文档问答的数据发送控制

## 为什么增加这些功能

企业资料问答的一个使用障碍是：用户无法判断上传、检索和回答分别在哪处理，也不知道历史问答是否会发给另一个模型。即使答案附带真实原文，数据接收方不清楚仍会影响使用意愿。

这里的需求来自项目使用方式分析，目前没有企业访谈或线上行为数据支持。此次迭代用于验证产品流程和技术可行性，不宣称已验证市场需求。

目标用户假设是使用企业知识文档、且企业已有批准模型服务的员工。部署者维护可用服务清单，员工只选择清单内的服务。当前没有管理员账号；“部署者”指有能力修改部署配置的人。

## 产品闭环

1. 上传前说明文件会进入应用服务器，解析与检索在服务器执行。
2. 展示服务提供方、端点、模型，以及候选原文、文件名、位置和历史问答的发送范围。
3. 用户允许当前文档发送，或选择禁止调用模型。发送范围变化后重新确认。
4. 获得 AI 回答时检查引用；禁止调用时提供关键词原文检索，不生成答案。
5. 每轮保留服务、模型、历史发送设置和调用编号；用户可导出记录、撤回许可、调整范围。

许可只控制本应用当前会话发起的请求，不证明已经取得企业授权。

## 几个取舍

### 为什么不自动判断文档是否机密

没有企业分类规则、标签来源和已验证识别效果。贸然自动判为“不敏感”会让用户误以为内容可以发出。本版由用户明确设置禁止；自动敏感识别、脱敏和企业策略属于后续独立能力。

### 为什么禁止后仍提供原文检索

不愿发送给模型不等于不需要查询。复用原有 BM25 排序和带位置的片段，可以提供有限但真实的价值。页面明确显示候选原文，用户自行阅读，不用“回答成功”包装检索结果。

“仅检索原文”不触发回答 API 或向量模型下载。上传和处理仍发生在应用服务器，因此它不是浏览器端离线工具。

### 为什么给历史发送单独开关

追问改写需要最近三轮有效问题与回答。用户切换到另一服务时，历史可能含先前服务返回的内部信息。关闭后不发送历史文本，直接检索本轮完整问题；代价是不能自动补全“那他们呢”这类省略。

页面保留历史是为了回看；保留与允许再次发送是两个不同决定。每轮记录当时设置，避免之后修改开关造成历史标记错误。

### 为什么不宣称可直接追责

应用 UUID 能关联本地调用记录，提供方名称来自部署配置，模型名来自请求参数。没有独立认证、服务商凭证、持久化或防篡改措施，不能由记录证明某服务商泄漏。SHA-256 标识也不能保证匿名化。

## 实现位置

- `model_services.py`：按文档维护禁止集合；许可绑定服务配置指纹、文档标识和历史发送设置；每次模型调用再次检查。请求拒绝重定向，不跨服务回退。
- `rag_core.py`：把原有检索步骤提取为 `retrieve_document`，模型问答和原文查询共用同一排序方法，没有改变检索算法或引用校验规则。
- `app.py`：上传与数据流说明、服务选择、文档禁止开关、历史范围选项、重新确认及原文结果展示。
- `conversation.py`：逐轮服务、模型、调用编号及历史发送设置；Markdown 导出保留这些信息。

浏览器流程使用受控的 `ModelSession`。命令行在线开发评测必须指定部署配置中的服务，并显式允许发送虚构评测资料和问答；它不读取浏览器会话内的文档禁止状态。兼容的 `call_llm` 函数仍由调用者显式发起，使用腾讯环境配置。若要生产级统一管控，需要将企业策略移至共享后端，在所有入口强制执行。

## 验收标准

| 场景 | 预期行为 | 验证方式 |
| --- | --- | --- |
| 未确认文档接收方 | 提问禁用，模型请求为零 | 界面和调用层测试 |
| 已确认后禁止发送 | 旧许可失效；回答和改写均阻断 | 模拟请求计数 |
| 禁止时查原文 | 展示带位置的片段，不调用模型 | 界面与检索测试 |
| 解除禁止 | 不恢复旧许可，需要重新确认 | 会话及界面测试 |
| 改变历史发送范围 | 许可失效 | 会话及界面测试 |
| 关闭历史后继续提问 | 无改写请求；按独立问题回答；旧记录保留 | 请求阶段和导出检查 |
| 切换服务或文档 | 重新确认；旧回答保留原服务标记 | 模型路由和界面测试 |
| 请求失败或重定向 | 报告错误，不更换接收方 | 模拟错误响应 |

## 后续如何验证价值

先找愿意试用的企业知识工作者，确认他们是否真的担心接收方不明、哪些文档不能外发，以及配置批准服务是否符合实际工作流程。不要预先假定所有用户都需要多模型。

可观察确认步骤完成率、取消原因、原文查询是否帮助完成任务、误认为“禁止发送等于文件未上传”的比例，以及切换服务时对历史发送的理解。与原版进行任务测试时，同时记录任务完成情况和总用时，检查新增控制是否造成过多阻碍。

这些是待验证的指标；当前没有真实用户数据，也没有需求转化率或效率提升结果。

## 2026-10-07 追加流程

现增加可选逐次发送预览与同服务条件核对，界面可取三处或最多六处原文。详见 [信任流程说明](trust-workflow.md)。开启核对增加本轮问题、候选原文和生成回答的发送；预览逐次确认具体文本，取消不能撤回已发送请求。BM25 和向量排序算法不变，证据数量上限可选；禁止规则仍在统一调用层生效。
